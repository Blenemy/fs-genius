# Медиаконвейер

Сервис фоновой обработки видео и изображений: пользователь загружает файл, система в очереди жмёт,
режет превью и извлекает метаданные, показывает прогресс в реальном времени и присылает готовое
в Telegram.

**Техническое задание, версия 1.0** — рабочий ориентир для разработки.

| Слой | Стек |
|---|---|
| Фронтенд | React, TypeScript, Tailwind, shadcn/ui, Zustand |
| Бэкенд | Express, TypeScript, Prisma, MySQL, Redis |
| Очереди | BullMQ |
| Хранилище | MinIO (S3-совместимое) |
| Обработка | ffmpeg, sharp |
| Уведомления | Telegram Bot API, SMTP |

## 1. Цель и границы

Учебно-портфолийный проект, задача которого — показать работу с длительными задачами, файлами и
распределённой обработкой, а не очередной CRUD. Всё, что делает систему интересной, крутится вокруг
одного факта: **обработка видео занимает минуты, и её физически нельзя выполнить внутри HTTP-запроса.**

### Что система делает

- принимает изображения и видео, загруженные напрямую в объектное хранилище;
- извлекает метаданные (размеры, длительность, кодек, битрейт);
- генерирует производные: миниатюры, превью, постер-кадр, перекодированное видео, аудиодорожку;
- показывает ход обработки в реальном времени, позволяет отменить задачу;
- переживает падение воркера: задача возвращается в очередь, мусор убирается;
- уведомляет о готовности в Telegram и отдаёт ссылку на скачивание.

### Чего система не делает

- не редактирует медиа (обрезка, склейка, фильтры) — только производит производные по пресетам;
- не стримит видео и не строит HLS-плейлисты (кандидат на будущее, вне первой версии);
- не хранит файлы вечно — у каждого актива есть срок жизни;
- не мультитенантна: пользователь видит только свои файлы, организаций и команд нет.

> **Ориентир.** Первая рабочая версия должна уметь загрузить фото, сделать три миниатюры и показать
> их в интерфейсе. Всё остальное наращивается поверх — этапы в разделе 14.

## 2. Сценарии

### Основной путь

1. Пользователь регистрируется, входит, попадает в библиотеку файлов.
2. Перетаскивает файл в зону загрузки. Браузер отправляет файл **напрямую в хранилище** по временной
   ссылке, минуя сервер приложения; на экране виден прогресс загрузки.
3. После загрузки сервер проверяет файл и ставит задачу в очередь. Актив получает статус `queued`.
4. Воркер забирает задачу, извлекает метаданные, генерирует производные. Прогресс идёт на фронт
   и обновляет полосу в карточке файла.
5. По завершении карточка показывает превью и список готовых вариантов, а в Telegram приходит
   сообщение с миниатюрой и ссылкой.

### Отклонения, которые обязаны работать

| Ситуация | Ожидаемое поведение |
|---|---|
| **Отмена** | Пользователь жмёт «Отменить» на выполняющейся задаче. Процесс ffmpeg убивается за несколько секунд, временные файлы удаляются, статус — `canceled`. |
| **Падение воркера** | Контейнер убит посреди обработки. Задача возвращается в очередь и подхватывается другим воркером; частично записанные файлы не попадают в выдачу. |
| **Битый файл** | ffprobe не может прочитать файл. Задача падает без ретраев, статус `failed` с понятной причиной в интерфейсе. |
| **Брошенная загрузка** | Пользователь закрыл вкладку на середине. Через сутки уборщик удаляет незавершённый актив и объект в хранилище, если он всё-таки долетел. |

## 3. Инфраструктура

Всё поднимается одной командой. Локальная разработка не должна зависеть от того, что установлено
на машине — кроме Node и Docker.

| Сервис | Роль | Порт |
|---|---|---|
| MySQL 8 | основное хранилище, работает через Prisma | `3306` |
| Redis 7 | очереди BullMQ, pub/sub для прогресса, кеш | `6379` |
| MinIO | S3-совместимое хранилище файлов + веб-консоль | `9000` / `9001` |
| Mailpit | перехват писем в разработке | `8025` |
| api | Express, HTTP и SSE | `3000` |
| worker | обработчик очередей, ffmpeg и sharp внутри | — |
| web | Vite dev-сервер React-приложения | `5173` |

> **Важно.** Образ воркера собирается с установленным `ffmpeg` — это не npm-пакет, а системный
> бинарник. Не тащи его в образ API: там он не нужен и только раздувает сборку.

### Структура репозитория

```
media-pipeline/
├── docker-compose.yml
├── packages/
│   ├── shared/          типы, общие для api и worker (DTO, имена очередей, схемы задач)
│   ├── api/             Express: HTTP, SSE, постановка задач
│   ├── worker/          BullMQ-воркеры, ffmpeg и sharp
│   └── web/             React + Vite
└── prisma/
    └── schema.prisma    одна схема на api и worker
```

Ключевое решение: **api и worker — разные процессы с общей базой и общим Redis**. Общий код
(типы задач, имена очередей, Prisma-клиент) живёт в отдельном пакете, чтобы имя очереди
не разъехалось между отправителем и получателем.

## 4. Архитектура

Три независимых процесса и четыре внешних хранилища состояния. Ни один запрос пользователя
не ждёт обработку.

| Процесс | Ответственность |
|---|---|
| **api** | Аутентификация, выдача временных ссылок на загрузку, постановка задач в очередь, чтение статусов из БД, трансляция прогресса по SSE. **Никогда не обрабатывает медиа и не проксирует тело файла.** |
| **worker** | Забирает задачи из Redis, качает исходник из хранилища во временную папку, гоняет ffmpeg или sharp, заливает результат обратно, пишет статус в MySQL и публикует прогресс в Redis. |
| **web** | Загружает файлы прямо в MinIO, слушает SSE, рисует библиотеку и прогресс. Не знает о существовании очередей. |
| **bot** | Отдельная точка входа (может жить внутри api): привязка аккаунта, приём команд, отправка уведомлений через очередь доставки. |

### Кто где хранит состояние

| Хранилище | Что лежит | Источник истины для |
|---|---|---|
| MySQL | пользователи, активы, задачи, производные, привязки Telegram | всего, что переживает перезапуск |
| Redis | очереди задач, флаги отмены, канал прогресса | текущего хода выполнения |
| MinIO | оригиналы и производные файлы | байтов |
| ФС воркера | временные файлы обработки | ничего — считается расходником |

> Прогресс живёт **только в Redis** и пишется в MySQL лишь на переходах статуса. Иначе обновление
> прогресса каждые полсекунды на каждой задаче превратит базу в узкое место.

## 5. Модель данных

Ключевое разделение: **актив** — то, что загрузил пользователь; **задача** — единица работы;
**производная** — файл-результат. Одна задача может породить несколько производных, у одного актива
может быть несколько задач.

```prisma
model User {
  id           String   @id @default(cuid())
  email        String   @unique
  passwordHash String
  role         Role     @default(USER)
  quotaBytes   BigInt   @default(2147483648)   // 2 ГБ на пользователя
  createdAt    DateTime @default(now())

  assets       Asset[]
  telegram     TelegramAccount?
}

model Asset {
  id           String      @id @default(cuid())
  userId       String
  originalName String      @db.VarChar(255)
  mimeType     String      @db.VarChar(100)
  sizeBytes    BigInt
  sha256       String?     @db.Char(64)        // для дедупликации
  storageKey   String      @unique             // ключ оригинала в S3
  kind         AssetKind                       // IMAGE | VIDEO
  status       AssetStatus @default(PENDING)

  // метаданные, заполняются на стадии probe
  width        Int?
  height       Int?
  durationMs   Int?
  codec        String?     @db.VarChar(50)
  bitrate      Int?

  expiresAt    DateTime?
  createdAt    DateTime    @default(now())

  user         User        @relation(fields: [userId], references: [id], onDelete: Cascade)
  jobs         Job[]
  derivatives  Derivative[]

  @@index([userId, createdAt])
  @@index([status])
}

model Job {
  id          String    @id @default(cuid())
  assetId     String
  type        JobType                          // PROBE | IMAGE_VARIANTS | VIDEO_TRANSCODE | AUDIO_EXTRACT
  status      JobStatus @default(QUEUED)
  progress    Int       @default(0)            // 0..100, снимок на переходах
  attempts    Int       @default(0)
  error       String?   @db.Text
  presetKey   String?   @db.VarChar(50)
  queueJobId  String?   @db.VarChar(100)       // id задачи в BullMQ, нужен для отмены
  startedAt   DateTime?
  finishedAt  DateTime?
  createdAt   DateTime  @default(now())

  asset       Asset     @relation(fields: [assetId], references: [id], onDelete: Cascade)
  derivatives Derivative[]

  @@index([assetId])
  @@index([status, createdAt])
}

model Derivative {
  id          String     @id @default(cuid())
  assetId     String
  jobId       String?
  kind        DerivKind                        // THUMBNAIL | PREVIEW | POSTER | VIDEO_720P | AUDIO_MP3
  storageKey  String     @unique
  mimeType    String     @db.VarChar(100)
  sizeBytes   BigInt
  width       Int?
  height      Int?
  createdAt   DateTime   @default(now())

  asset       Asset      @relation(fields: [assetId], references: [id], onDelete: Cascade)
  job         Job?       @relation(fields: [jobId], references: [id], onDelete: SetNull)

  @@index([assetId, kind])
}

model TelegramAccount {
  id        String   @id @default(cuid())
  userId    String   @unique
  chatId    BigInt   @unique
  username  String?  @db.VarChar(100)
  isActive  Boolean  @default(true)            // false после блокировки бота
  linkedAt  DateTime @default(now())

  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}

model TelegramLinkToken {
  token     String   @id @db.VarChar(64)
  userId    String
  expiresAt DateTime
  usedAt    DateTime?
}

enum Role        { USER ADMIN }
enum AssetKind   { IMAGE VIDEO }
enum AssetStatus { PENDING UPLOADED PROCESSING READY FAILED }
enum JobType     { PROBE IMAGE_VARIANTS VIDEO_TRANSCODE AUDIO_EXTRACT }
enum JobStatus   { QUEUED RUNNING DONE FAILED CANCELED }
enum DerivKind   { THUMBNAIL PREVIEW POSTER VIDEO_720P AUDIO_MP3 }
```

### Статусы актива

| Статус | Значение |
|---|---|
| `PENDING` | ссылка выдана, файла ещё нет |
| `UPLOADED` | файл в хранилище, проверен |
| `PROCESSING` | есть активная задача |
| `READY` | все задачи завершены |
| `FAILED` | обработка невозможна |

> `BigInt` для размеров — не педантизм: видео легко переваливает за два гигабайта, а `Int` в MySQL
> заканчивается на 2 147 483 647. Помни, что `BigInt` не сериализуется в JSON сам по себе — приводи
> к строке или числу на границе API.

## 6. Хранилище файлов

### Прямая загрузка мимо сервера

Express **не принимает тело файла**. Клиент запрашивает временную ссылку, кладёт файл прямо в MinIO
и сообщает серверу, что закончил. Причина простая: файл на два гигабайта, проходящий через Node,
занимает соединение на минуты и упирается в память и таймауты.

1. `POST /api/uploads/presign` — сервер проверяет квоту и тип, создаёт запись `Asset` со статусом
   `PENDING`, генерирует ключ и возвращает временную ссылку на запись (живёт 15 минут).
2. Браузер делает `PUT` по этой ссылке и отслеживает прогресс загрузки.
3. `POST /api/uploads/:id/complete` — сервер запрашивает у хранилища размер объекта, сверяет
   с заявленным, читает первые байты для проверки формата, переводит актив в `UPLOADED`
   и ставит задачу `PROBE`.

### Схема ключей

```
u/{userId}/{assetId}/original.{ext}
u/{userId}/{assetId}/thumb_320.webp
u/{userId}/{assetId}/preview_1280.webp
u/{userId}/{assetId}/poster.jpg
u/{userId}/{assetId}/video_720p.mp4
u/{userId}/{assetId}/audio.mp3
```

Имя, которое дал пользователь, **никогда не участвует в построении пути** — только в отображении.
Иначе файл с именем `../../etc/passwd` или с юникодом ломает всё, от путей до заголовков ответа.

### Раздача результатов

Бакет закрытый. Скачивание — через временную ссылку на чтение, которую выдаёт API после проверки
прав (срок жизни — час). Миниатюры в интерфейсе — то же самое, но со сроком жизни в сутки,
чтобы браузер мог их кешировать.

## 7. Конвейер обработки

```
[1] Приём ──▶ [2] Probe ──▶ [3] Ветвление ──▶ [4] Обработка ──▶ [5] Выгрузка ──▶ [6] Уведомление
 проверка      ffprobe /     изображение и      sharp или        результаты      Telegram и
 размера,      sharp:        видео уходят       ffmpeg,          в S3, записи    почта через
 квоты,        размеры,      в разные           прогресс         Derivative      очередь
 сигнатуры     длительность  очереди            в Redis          в БД            доставки
```

### Изображения (sharp)

| Производная | Параметры | Формат |
|---|---|---|
| `THUMBNAIL` | вписать в 320×320, сохранить пропорции | WebP, q80 |
| `PREVIEW` | вписать в 1280×1280, не увеличивать | WebP, q82 |

EXIF-ориентацию применить и вырезать: поворот должен быть «вшит» в пиксели, а геометки пользователя
не должны утекать в публичные превью.

### Видео (ffmpeg)

| Производная | Параметры | Зачем |
|---|---|---|
| `POSTER` | кадр на 10% длительности, вписать в 1280 | обложка в библиотеке |
| `THUMBNAIL` | тот же кадр, 320 | сетка карточек |
| `VIDEO_720P` | H.264, высота 720, CRF 23, preset veryfast, AAC 128k, `+faststart` | единый формат для просмотра |
| `AUDIO_MP3` | моно, 64 кбит/с | задел под транскрибацию |

> **Безопасность.** ffmpeg запускается **только через массив аргументов**. Никакой сборки строки
> команды и никакого shell: любое пользовательское значение, попавшее в строку, — это выполнение
> произвольного кода на сервере. Флаг `+faststart` обязателен, иначе видео не начнёт играть
> в браузере до полной загрузки.

### Правило временных файлов

Воркер работает во временной директории, уникальной для задачи. Директория удаляется в блоке
`finally` — при успехе, ошибке и отмене одинаково. Результат считается готовым только после
успешной выгрузки в хранилище и записи в БД; порядок именно такой, иначе в базе появятся ссылки
на несуществующие файлы.

## 8. Очереди

BullMQ поверх Redis. Разные типы работ — **разные очереди**, потому что у них принципиально разные
требования к параллелизму: перекодирование видео забивает процессор целиком, а отправка сообщения
в Telegram ждёт сеть.

| Очередь | Параллелизм | Ретраи | Таймаут | Заметки |
|---|---|---|---|---|
| `media:probe` | 4 | 2, экспоненциально | 30 с | быстрая, читает только начало файла |
| `media:image` | ядра − 1 | 2 | 2 мин | sharp с ограничением на размер входа |
| `media:video` | 1–2 | 1 | 30 мин | главный потребитель CPU, держать отдельно |
| `notify` | 5 | 3 | 15 с | ограничение частоты под лимиты Telegram |
| `cleanup` | 1 | — | 5 мин | по расписанию, раз в час |

### Что не ретраить

Разделяй ошибки на временные и окончательные. Сеть отвалилась, хранилище недоступно, Telegram
ответил `429` — повторяем. Файл не является видео, кодек не поддерживается, пользователь удалил
актив, бот заблокирован — **повторять бессмысленно**, задача падает сразу и пишет причину.
Три попытки перекодировать битый файл по полчаса каждая — верный способ забить очередь.

### Хранение истории

Успешные задачи удаляются из Redis сразу (данные уже в MySQL), упавшие — хранятся сутки, чтобы можно
было посмотреть стек. Redis не архив: очередь, забитая историей за месяц, съедает память.

### Уборщик

- активы в `PENDING` старше 24 часов — удалить вместе с объектом в хранилище;
- объекты в хранилище, которых нет в БД (следы упавших задач) — удалить;
- активы с истёкшим `expiresAt` — удалить каскадно;
- временные директории воркера старше суток — удалить.

## 9. Прогресс и отмена

### Как прогресс доезжает до браузера

Здесь главная архитектурная тонкость: **прогресс рождается в воркере, а SSE-соединение держит API** —
это разные процессы. Связывает их Redis:

1. ffmpeg запускается с выводом прогресса в поток; воркер парсит текущую позицию и делит
   на длительность из стадии probe;
2. не чаще раза в секунду воркер публикует в канал Redis сообщение вида
   `{ jobId, assetId, userId, status, progress }`;
3. API подписан на канал и рассылает событие тем SSE-клиентам, чей `userId` совпал;
4. фронт получает событие и обновляет полосу прогресса.

**Почему SSE, а не WebSocket:** поток односторонний — сервер сообщает, клиент только слушает.
SSE работает поверх обычного HTTP, сам переподключается при обрыве и не требует отдельного протокола.
WebSocket понадобился бы, если бы клиент слал что-то в ответ.

> **Не забудь.** При открытии SSE-соединения первым делом отправь **текущее состояние** всех активных
> задач пользователя. Иначе после перезагрузки страницы полоса будет висеть на нуле до следующего
> события — а его может не быть ещё полминуты.

### Отмена

Два разных случая, и путать их нельзя:

- **Задача ещё в очереди** — просто удаляем её из очереди, статус `CANCELED`. Никто ничего не заметил.
- **Задача уже выполняется** — воркер не читает базу в цикле, поэтому нужен сигнал: API ставит
  в Redis ключ `cancel:{jobId}`, воркер проверяет его между стадиями и при получении убивает дочерний
  процесс ffmpeg, чистит временную папку и завершает задачу как отменённую.

Отмена не мгновенная. Интерфейс должен показывать промежуточное состояние «отменяется», а не делать
вид, что всё уже кончилось. Если процесс не умер за 10 секунд по мягкому сигналу — убивать жёстко.

## 10. HTTP API

REST, JSON, префикс `/api`. Аутентификация — access-токен в заголовке, refresh-токен
в httpOnly-cookie.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/register` | регистрация |
| `POST` | `/auth/login` | вход, выдача пары токенов |
| `POST` | `/auth/refresh` | обновление access-токена |
| `POST` | `/auth/logout` | отзыв refresh-токена |
| `POST` | `/uploads/presign` | ссылка на загрузку + черновик актива |
| `POST` | `/uploads/:id/complete` | подтверждение загрузки, запуск конвейера |
| `GET` | `/assets` | библиотека: страница, фильтр по типу и статусу |
| `GET` | `/assets/:id` | актив с задачами и производными |
| `DELETE` | `/assets/:id` | удаление актива и всех файлов |
| `GET` | `/assets/:id/download` | временная ссылка на файл или производную |
| `POST` | `/assets/:id/jobs` | перезапуск или новая обработка по пресету |
| `POST` | `/jobs/:id/cancel` | отмена задачи |
| `GET` | `/events` | SSE-поток прогресса текущего пользователя |
| `POST` | `/telegram/link` | одноразовая ссылка привязки бота |
| `DELETE` | `/telegram/link` | отвязка |
| `POST` | `/telegram/webhook` | приём обновлений от Telegram |
| `GET` | `/health` | состояние БД, Redis и хранилища |

### Единый формат ошибок

```json
{
  "error": {
    "code": "FILE_TOO_LARGE",
    "message": "Файл больше 2 ГБ",
    "details": { "maxBytes": 2147483648 }
  }
}
```

Машиночитаемый `code` — для фронта, `message` — для человека. Одна общая middleware в конце цепочки;
в контроллерах не должно быть ни единого `res.status(500)` вручную.

## 11. Telegram

### Привязка аккаунта

Бот не может написать первым — это ограничение Telegram. Поэтому: пользователь в настройках жмёт
«Привязать Telegram», сервер создаёт одноразовый токен и показывает ссылку `t.me/бот?start=ТОКЕН`.
Пользователь открывает её, Telegram отправляет боту `/start ТОКЕН`, сервер находит токен, сохраняет
`chatId` и гасит токен. Срок жизни токена — 10 минут.

### Уведомления

- обработка завершена — миниатюра, имя файла, список готовых вариантов, ссылка на скачивание;
- обработка упала — имя файла и причина;
- ничего не слать по каждой мелкой стадии: одно сообщение на завершённый актив, а не на задачу.

### Команды

| Команда | Ответ |
|---|---|
| `/start` | привязка либо приветствие уже привязанному |
| `/status` | сколько задач в работе и в очереди |
| `/last` | пять последних готовых файлов со ссылками |
| `/stop` | отключить уведомления, не удаляя привязку |

### Правила отправки

- режим разметки — **HTML**, а не MarkdownV2: экранировать нужно три символа вместо полутора десятков;
- сообщение длиннее ~4096 символов резать на части по границам строк;
- ответ `429` содержит `retry_after` — использовать его как задержку повторной попытки, а не гадать;
- ответ `403` означает, что бот заблокирован: пометить привязку неактивной и **перестать слать**,
  а не ретраить;
- локально — режим опроса, в проде — webhook: для webhook нужен публичный HTTPS.

> **Секрет.** Токен бота даёт полный контроль над ним. Только в переменных окружения, никогда в коде
> и никогда в репозитории. Вебхук защищать секретным токеном в заголовке — иначе кто угодно сможет
> присылать поддельные «обновления».

## 12. Фронтенд

### Экраны

| Экран | Содержимое |
|---|---|
| Вход / регистрация | форма, обработка ошибок валидации с сервера |
| Библиотека | сетка карточек с превью, статусом и полосой прогресса; фильтры по типу и статусу; бесконечная лента или страницы |
| Загрузка | перетаскивание, очередь загрузок с индивидуальным прогрессом, отмена |
| Карточка файла | превью или плеер, метаданные, список производных со скачиванием, история задач, кнопки отмены и перезапуска |
| Настройки | привязка Telegram, квота и занятое место, срок хранения |

### Состояние (Zustand)

| Стор | Содержимое |
|---|---|
| `authStore` | пользователь, access-токен в памяти, refresh — через cookie. Токен не в localStorage |
| `uploadStore` | очередь загрузок: файл, прогресс, статус, отмена. Живёт отдельно от библиотеки, потому что загрузка идёт в браузере, а не на сервере |
| `assetsStore` | страница библиотеки, фильтры, кеш карточек. Обновляется по событиям SSE точечно, без перезагрузки всего списка |
| `eventsStore` | одно SSE-соединение на приложение, переподключение с задержкой, раздача событий подписчикам |

> Одно соединение на всё приложение, а не по одному на карточку. Двадцать карточек в сетке — это
> двадцать соединений и мгновенно исчерпанный лимит браузера.

### Компоненты shadcn/ui

Диалоги (подтверждение удаления), `Progress` для полос, `Badge` для статусов, `Table` для истории
задач, `Tabs` в карточке файла, `Skeleton` на загрузке, тосты для уведомлений. Статусы задать
**цветом и формой** — не только текстом: состояние должно читаться взглядом по сетке.

### Что должно работать без обновления страницы

- полоса прогресса ползёт;
- карточка сама превращается из «в обработке» в готовую с превью;
- отменённая задача сразу переходит в «отменяется», потом в «отменена»;
- после перезагрузки страницы состояние восстанавливается полностью.

## 13. Ограничения и безопасность

| Параметр | Значение |
|---|---|
| Максимальный размер файла | 2 ГБ видео, 50 МБ изображение |
| Максимальная длительность видео | 30 минут |
| Квота пользователя | 2 ГБ суммарно |
| Одновременных задач на пользователя | 3 (остальные ждут) |
| Допустимые типы | jpeg, png, webp, heic, mp4, mov, webm, mkv |
| Срок хранения | 30 дней с момента загрузки |

### Проверки, которые нельзя пропустить

- **Тип файла — по сигнатуре, а не по расширению и не по заголовку от клиента.** Расширение `.jpg`
  ничего не значит: и то, и другое присылает браузер, а браузером управляет пользователь.
- **Ограничить размер входного изображения в пикселях.** Файл на 2 МБ может распаковаться
  в 50 000 × 50 000 пикселей и положить воркер по памяти — это известная атака, и sharp умеет
  от неё защищаться настройкой.
- **Проверять принадлежность актива пользователю в каждом запросе.** Идентификаторы непредсказуемы,
  но это не защита: проверка владельца обязательна и в скачивании, и в отмене.
- **Ограничение частоты** на выдачу ссылок для загрузки — иначе можно наплодить тысячи черновиков.
- **Никакого пользовательского ввода в аргументах ffmpeg** — только собственные ключи из базы
  и константы пресетов.

### Наблюдаемость

- структурные логи с идентификатором запроса и задачи, а не `console.log`;
- метрики: длина очередей, время обработки по типам, доля падений;
- `/health` проверяет доступность MySQL, Redis и хранилища по отдельности.

## 14. Этапы

Порядок не случайный: каждый этап заканчивается чем-то, что запускается и работает. Не начинай
следующий, пока предыдущий не доведён до конца.

### M0 — Фундамент

Ничего пользовательского, только рельсы.

- [ ] docker-compose: MySQL, Redis, MinIO, Mailpit — поднимается одной командой
- [ ] монорепозиторий, общие типы, TypeScript и линтер во всех пакетах
- [ ] Prisma подключена, первая миграция применена
- [ ] `/health` отвечает и честно проверяет все три хранилища

### M1 — Аккаунты и загрузка

Файл долетает до хранилища, но ещё ничего не обрабатывается.

- [ ] регистрация, вход, refresh-токены, общая middleware ошибок
- [ ] выдача временных ссылок и подтверждение загрузки с проверкой формата
- [ ] библиотека со списком загруженного
- [ ] фронт: вход, перетаскивание файла, прогресс загрузки

### M2 — Очередь и изображения

Первая настоящая фоновая обработка и первый живой прогресс.

- [ ] воркер отдельным процессом, очереди `probe` и `image`
- [ ] sharp: миниатюра и превью, записи производных
- [ ] прогресс через Redis pub/sub, SSE на API, полоса на фронте
- [ ] карточка файла с готовыми вариантами

### M3 — Видео и отмена

Самый содержательный этап — ради него всё затевалось.

- [ ] ffprobe и ffmpeg в образе воркера, очередь `video` с малым параллелизмом
- [ ] постер, перекодирование в 720p, извлечение аудио
- [ ] реальный прогресс из вывода ffmpeg
- [ ] отмена в обоих вариантах: из очереди и на лету
- [ ] проверка выживания при убийстве воркера посреди обработки

### M4 — Telegram

Второй канал доставки и первая внешняя интеграция.

- [ ] привязка через одноразовую ссылку
- [ ] очередь уведомлений с ограничением частоты и разбором `429` и `403`
- [ ] сообщение о готовности с миниатюрой и ссылкой
- [ ] команды `/status`, `/last`, `/stop`

### M5 — Устойчивость

То, что отличает проект-игрушку от проекта, который не стыдно показать.

- [ ] уборщик по расписанию: черновики, сироты, истёкшие активы
- [ ] квоты, ограничения частоты, лимит одновременных задач
- [ ] структурные логи и метрики очередей
- [ ] тесты: пайплайн изображения от загрузки до готовности, отмена, отказ на битом файле

### M6 — Необязательное

Только после того, как всё выше работает.

- [ ] транскрибация аудиодорожки и поиск по содержимому видео
- [ ] составная загрузка для файлов больше двух гигабайт
- [ ] спрайт-лента кадров для перемотки
- [ ] деплой на реальный сервер с доменом и HTTPS

## 15. Критерии приёмки

Проверяемые утверждения. Если хотя бы одно не выполняется — этап не закрыт.

- [ ] Файл на 500 МБ загружается, при этом процесс API не растёт по памяти и не держит соединение
- [ ] Видео на 5 минут обрабатывается, полоса прогресса движется не рывками от 0 к 100
- [ ] Кнопка «Отменить» останавливает обработку не дольше чем за 10 секунд, временные файлы исчезают
- [ ] Контейнер воркера убит на середине обработки — после перезапуска задача выполняется заново и завершается успешно
- [ ] Переименованный в `.mp4` текстовый файл отклоняется на этапе подтверждения загрузки
- [ ] Перезагрузка страницы во время обработки восстанавливает прогресс без потери состояния
- [ ] Два файла загружаются одновременно, оба обрабатываются, прогресс у каждого свой
- [ ] Сообщение в Telegram приходит один раз на актив, а не на каждую внутреннюю задачу
- [ ] Заблокировавший бота пользователь не порождает бесконечных повторов в очереди уведомлений
- [ ] Ссылка на скачивание чужого файла возвращает отказ, а не файл
- [ ] Истёкшая временная ссылка перестаёт работать
- [ ] Уборщик удаляет незавершённый актив старше суток вместе с объектом в хранилище

## 16. Грабли

Собрано заранее, чтобы не открывать заново.

| Грабли | Суть |
|---|---|
| **Прогресс между процессами** | Самая частая ошибка — писать прогресс в память API. Воркер это другой процесс, его переменные API не видит. Только Redis. |
| **Слишком частые записи в БД** | Обновление `progress` в MySQL на каждый процент — это сотни запросов в секунду. В базу пишем только смену статуса. |
| **Параллелизм видео** | Четыре ffmpeg на четырёх ядрах кладут машину, и всё остальное перестаёт отвечать. Один-два, и не больше. |
| **Файл через Node** | Загрузка гигабайтов через Express съедает память и упирается в таймауты. Только прямая загрузка в хранилище. |
| **Сироты в хранилище** | Задача упала после выгрузки, но до записи в базу — файл есть, ссылки нет. Отсюда уборщик, а не «само не случится». |
| **Порядок операций** | Сначала выгрузить результат, потом записать производную в базу. Обратный порядок даёт битые ссылки в интерфейсе. |
| **Ввод в командной строке** | Имя файла, попавшее в строку команды ffmpeg, — это исполнение произвольного кода. Только массив аргументов. |
| **Ретраи там, где не надо** | Повторять перекодирование битого файла бесполезно и дорого. Разделяй временные ошибки и окончательные. |

> **Метод.** Каждый этап начинай с самого страшного места. Умеешь показать прогресс — остальное в M2
> дело техники. Умеешь отменить ffmpeg — M3 закрыт. Откладывание сложного на конец — главная причина,
> по которой пет-проекты не доживают до конца.

---

Документ — рабочий ориентир, а не догма. Меняй решения, если по ходу выяснится, что что-то устроено
удобнее, но меняй осознанно: почти каждое требование здесь стоит на конкретной причине, и причина
обычно описана рядом.
